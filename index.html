9.3

sql-on-fhir: SQL on FHIR🔗

A FHIR record is a nested document. A patient holds a list of names, and each name a list of given names; a blood pressure reading holds two measurements inside it. That shape suits passing records between systems. It does not suit counting them: a spreadsheet, a database or a statistics package wants a table, where every row has the same columns and every cell holds one value.

SQL on FHIR is the standard for getting from one to the other. You write a ViewDefinition: a short JSON file that says which kind of record you want, which columns the table has, and where in the record each column’s value is found. The same file works in any tool that follows the standard.

This package runs a ViewDefinition over your FHIR data and prints the table, as CSV for a spreadsheet or as JSON for a program. A mistake in the view is reported before anything runs.

Part of the fhir family of FHIR languages and tools.

1 What you can do with it🔗

  • Turn a folder of FHIR records into a table: A first example.

  • Get one row per record, or one row per repeated item inside it, such as each phone number or each measurement: One row per record, or one per repeated item.

  • Keep only the records you want: Keeping only some records.

  • Make tables that join, a table of readings and a table of patients sharing a patient id: Keys: tables that join.

  • Choose the output for what reads it next, a spreadsheet, a database loader or another FHIR system: Output formats, and what each is for.

  • Use a view from a program, as rows in Racket or as a FHIR operation over HTTP: From a Racket program and As a FHIR operation.

2 A first example🔗

1. Install the tools as the family’s front page describes. The command is then raco sql-on-fhir (or sql-on-fhir, if you built the standalone tools).

2. Have some records. The data is a folder of FHIR resources as JSON files, one record to a file. Here it is two patients in data/. Ann has two given names and two phone numbers; Bob has one given name and no phone.

{"resourceType": "Patient", "id": "ann", "gender": "female", "birthDate": "1974-12-25",

 "name": [{"family": "Lee", "given": ["Ann", "Marie"]}],

 "telecom": [{"system": "phone", "value": "555-0100", "use": "home"},

             {"system": "phone", "value": "555-0101", "use": "work"}]}

 

{"resourceType": "Patient", "id": "bob", "gender": "male", "birthDate": "1990-03-01",

 "name": [{"family": "Ortiz", "given": ["Bob"]}]}

3. Write a view, patients.view.json:

{

  "resourceType": "ViewDefinition",

  "name": "patients",

  "status": "active",

  "resource": "Patient",

  "select": [

    {"column": [

      {"name": "id", "path": "getResourceKey()"},

      {"name": "family", "path": "name.family.first()"},

      {"name": "gender", "path": "gender"},

      {"name": "birth_date", "path": "birthDate"}]}

  ]

}

Reading it from the top:

  • resourceType says this file is a ViewDefinition. name is the table’s name. status is required by the standard; write "active".

  • resource is the kind of record the table is made from. Every Patient in the data becomes a row; records of other kinds are passed over.

  • select holds the columns. Each column has a name, the heading it gets in the table, and a path, which says where its value is in the record.

  • A path is written in FHIRPath, the small language FHIR uses to point into a record. gender is the record’s gender. name.family.first() goes into the names, takes each one’s family name, and keeps the first. getResourceKey() is the record’s id.

4. Run it over the folder:

$ raco sql-on-fhir run patients.view.json data/ --format csv

id,family,gender,birth_date

ann,Lee,female,1974-12-25

bob,Ortiz,male,1990-03-01

One heading line, then one row for each patient, with the columns in the order the view lists them. --format csv asks for comma-separated text, which a spreadsheet opens directly. The other formats are in Output formats, and what each is for.

5. Make a mistake. Add a column for the given name, with the path name.given. Ann has two given names, and a cell holds one value, so the view is refused:

$ raco sql-on-fhir run given.view.json data/ --format csv

sql-on-fhir: column given: path yields 2 items without collection=true

This is the central difficulty of flattening, and there are three ways out. Take one value (name.given.first()). Ask for a row per value (One row per record, or one per repeated item). Or say the cell may hold a list, by adding "collection": true to the column:

$ raco sql-on-fhir run given2.view.json data/

{"given":["Ann","Marie"],"id":"ann"}

{"given":["Bob"],"id":"bob"}

3 Writing a view🔗

A view picks a kind of record, optionally filters it, and lists columns. This section takes those one idea at a time. The format itself is defined by the SQL on FHIR specification; the paths are FHIRPath.

3.1 A column is a path🔗

A column’s path starts at the record and walks inward, one element name after another, with dots between: birthDate, name.family, code.coding.code. Where an element repeats, the path gives every value, so you often finish with something that picks one:

  • name.family.first(): the first of them.

  • name.where(use = 'official').family: only from the names that match a condition.

  • telecom.where(system = 'phone').value.first(): both together.

A path that finds nothing gives an empty cell (null in JSON), not an error. A path that names an element the record type does not have is refused, with the name you probably meant:

sql-on-fhir: fhirpath: no element Patient.gendr (did you mean `gender`?)

Some FHIR elements can hold one of several types, and are written with the type in their name: an Observation’s value is valueQuantity or valueString, its time effectiveDateTime or effectivePeriod. In a path you write the plain name and then say which type you mean: value.ofType(Quantity).value is the number of a quantity, effective.ofType(dateTime) a single moment.

A column may also carry a description, a type and tags. They are kept in the view for other tools and do not change the rows here.

3.2 One row per record, or one per repeated item🔗

By default a view gives one row for each record. To get a row for each item of a repeating element instead (each phone number, each measurement in a panel), put those columns in a part of the select that says forEach. This is phones.view.json:

{

  "resourceType": "ViewDefinition",

  "name": "phones",

  "status": "active",

  "resource": "Patient",

  "select": [

    {"column": [{"name": "id", "path": "getResourceKey()"}]},

    {"forEach": "telecom.where(system = 'phone')", "column": [

      {"name": "use", "path": "use"},

      {"name": "number", "path": "value"}]}

  ]

}

$ raco sql-on-fhir run phones.view.json data/ --format csv

id,use,number

ann,home,555-0100

ann,work,555-0101

The select now has two parts. The first has the columns that are about the whole record. The second has a forEach path, and its columns’ paths start at each item that path finds, not at the record: use here is the phone’s use. The parts are combined, so each phone’s row also carries the patient’s id.

Bob is missing: he has no phone, so there is no item to make a row from. When you want every record to appear at least once, write forEachOrNull in place of forEach. A record with no items then gets one row with those cells empty:

$ raco sql-on-fhir run phones-all.view.json data/ --format csv

id,use,number

ann,home,555-0100

ann,work,555-0101

bob,,

A part of a select may contain a select of its own, for a list inside a list (each given name of each name). Inside a forEach, %rowIndex is the item’s position, counted from 0.

3.3 Keeping only some records🔗

A where is a filter: a path that is true or false for a record. Only the records for which it is true make rows. This view lists the women:

{

  "resourceType": "ViewDefinition",

  "name": "women",

  "status": "active",

  "resource": "Patient",

  "where": [{"path": "gender = 'female'"}],

  "select": [

    {"column": [

      {"name": "id", "path": "getResourceKey()"},

      {"name": "birth_date", "path": "birthDate"}]}

  ]

}

$ raco sql-on-fhir run women.view.json data/ --format csv

id,birth_date

ann,1974-12-25

Text is written in single quotes. When where lists several paths, a record must pass all of them. A path that finds nothing counts as false. A path that gives something other than true or false is a mistake in the view and is refused:

sql-on-fhir: where path must resolve to a boolean, got (Ann Marie)

The usual filter on clinical records is by code: "only the blood pressure readings" is code.coding.exists(system = 'http://loinc.org' and code = '85354-9'), as in the next example.

3.4 Keys: tables that join🔗

Records point at one another: a reading names the patient it belongs to. Two functions, which exist only in view paths, turn those links into values two tables share. getResourceKey() is a record’s own id. getReferenceKey(Patient) is the id of the patient a link names. So a table of readings and a table of patients can be joined on them.

Here are two blood pressure readings for Ann. Each is one Observation with two components, the systolic and the diastolic pressure, each with its own code:

{"resourceType": "Observation", "id": "bp-1", "status": "final",

"code": {"coding": [{"system": "http://loinc.org", "code": "85354-9"}]},

"subject": {"reference": "Patient/ann"}, "effectiveDateTime": "2024-03-01T09:00:00Z",

"component": [

  {"code": {"coding": [{"system": "http://loinc.org", "code": "8480-6"}]},

   "valueQuantity": {"value": 152, "unit": "mmHg", "system": "http://unitsofmeasure.org", "code": "mm[Hg]"}},

  {"code": {"coding": [{"system": "http://loinc.org", "code": "8462-4"}]},

   "valueQuantity": {"value": 95, "unit": "mmHg", "system": "http://unitsofmeasure.org", "code": "mm[Hg]"}}]}

The second, bp-2, is a month later with 138 over 88. This view, bp.view.json, makes a row for each measurement:

{

  "resourceType": "ViewDefinition",

  "name": "bp_readings",

  "status": "active",

  "resource": "Observation",

  "where": [{"path": "code.coding.exists(system = 'http://loinc.org' and code = '85354-9')"}],

  "select": [

    {"column": [

      {"name": "id", "path": "getResourceKey()"},

      {"name": "patient", "path": "subject.getReferenceKey(Patient)"},

      {"name": "date", "path": "effective.ofType(dateTime)"}]},

    {"forEach": "component", "column": [

      {"name": "code", "path": "code.coding.code.first()"},

      {"name": "value", "path": "value.ofType(Quantity).value"}]}

  ]

}

$ raco sql-on-fhir run bp.view.json data/ --format csv

id,patient,date,code,value

bp-1,ann,2024-03-01T09:00:00Z,8480-6,152

bp-1,ann,2024-03-01T09:00:00Z,8462-4,95

bp-2,ann,2024-04-02T09:30:00Z,8480-6,138

bp-2,ann,2024-04-02T09:30:00Z,8462-4,88

The patient column holds ann, the same value as the id column of the patients table in A first example. getReferenceKey reads links written the usual short way (Patient/ann); a link written as a full web address gives an empty cell.

3.5 Naming a value once🔗

When the same code or text appears in several paths, give it a name under constant and use it as %name. This view puts the two pressures side by side, one row per reading:

{

  "resourceType": "ViewDefinition",

  "name": "bp_wide",

  "status": "active",

  "resource": "Observation",

  "constant": [{"name": "systolic", "valueCode": "8480-6"}, {"name": "diastolic", "valueCode": "8462-4"}],

  "where": [{"path": "code.coding.exists(system = 'http://loinc.org' and code = '85354-9')"}],

  "select": [

    {"column": [

      {"name": "patient", "path": "subject.getReferenceKey(Patient)"},

      {"name": "date", "path": "effective.ofType(dateTime)"},

      {"name": "systolic", "path": "component.where(code.coding.code = %systolic).value.ofType(Quantity).value"},

      {"name": "diastolic", "path": "component.where(code.coding.code = %diastolic).value.ofType(Quantity).value"}]}

  ]

}

$ raco sql-on-fhir run bp-wide.view.json data/ --format csv

patient,date,systolic,diastolic

ann,2024-03-01T09:00:00Z,152,95

ann,2024-04-02T09:30:00Z,138,88

A constant’s value is written with its type, as FHIR does: valueCode, valueString, valueInteger, valueBoolean and so on.

3.6 Stacking rows, and lists inside lists🔗

Two more words cover the shapes that are left.

unionAll stacks the rows of several alternatives that have the same columns. This view lists each patient’s phones and then their names, in one table:

"select": [

  {"column": [{"name": "id", "path": "getResourceKey()"}],

   "unionAll": [

     {"forEach": "telecom", "column": [{"name": "kind", "path": "system"}, {"name": "text", "path": "value"}]},

     {"forEach": "name", "column": [{"name": "kind", "path": "'name'"}, {"name": "text", "path": "family"}]}]}

]

id,kind,text

ann,phone,555-0100

ann,phone,555-0101

ann,name,Lee

bob,name,Ortiz

repeat follows a path again and again, for records that nest to any depth. A filled-in questionnaire holds items that hold items; {"repeat": ["item"], "column": […]} gives a row for every item at every level:

id,link_id,text

qr1,1,About you

qr1,1.1,Smoker

qr1,1.2,Allergies

qr1,1.2.1,Penicillin

3.7 When a view is refused🔗

A view is checked against the standard’s own description of a ViewDefinition before it runs. Each problem is one line, and the command exits with status 1.

  • A misspelt word of the format (selct for select):

    sql-on-fhir: not a valid ViewDefinition: ViewDefinition: unknown field selct (see https://build.fhir.org/ig/FHIR/sql-on-fhir-v2/viewdefinition.html#ViewDefinition)

  • A value outside the allowed list (status, resource and fhirVersion each have one; a status is active, draft, retired or unknown):

    sql-on-fhir: not a valid ViewDefinition: "live" is not in the required value set for ViewDefinition.status (http://hl7.org/fhir/ValueSet/publication-status)

  • A path that gives several values for one cell: column given: path yields 2 items without collection=true. Narrow the path, use forEach, or mark the column as a collection (A first example, step 5).

  • A record is missing from the rows, with no message: a forEach over an element the record does not have drops it (forEachOrNull keeps it), or a where is false for it. To see which, run a view with only that path as a column.

  • A file that is not JSON: sql-on-fhir: view.json is not JSON: …, with the place reading stopped.

4 Running it🔗

4.1 Command line🔗

The command you will use is run. The others are for people working on the package itself.

raco sql-on-fhir run view.json data/ [--format ndjson|json|csv|fhir]

  

a view (JSON, or a #lang sql-on-fhir module of any extension) over a directory, Bundle or resource

raco sql-on-fhir tck [-v]

  

the shared test suite, with its report; -v prints each failure

raco sql-on-fhir regen

  

regenerate the ViewDefinition model from the specification’s package in spec/

raco sql-on-fhir check

  

verify the generated model is current

raco sql-on-fhir fetch [--version v] [--tests-commit sha]

  

download the specification's package and the test suite again (needs the network)

The data given to run is one of three things: a folder of JSON files, one record to a file; a single file holding a Bundle, which is FHIR’s envelope for many records in one file; or a single file holding one record. Only the records of the view’s resource kind are read; the rest are ignored. With no data at all, you get the heading and no rows.

Exit status: 0 when the table was printed; 1 when the view was refused, a file was not JSON, or the view failed on the data (each one line with the reason), and when the test suite regresses; 2 when the command was called wrongly, such as with a file that does not exist.

4.2 Output formats, and what each is for🔗

--format chooses how the same rows are written.

format

  

what you get

  

use it for

csv

  

a heading line, then one comma-separated line per row

  

a spreadsheet, or a database's import command

ndjson

  

one JSON object per line (the default)

  

data tools that read a file line by line, and large outputs

json

  

one JSON array holding every row

  

a program that reads the whole answer at once

fhir

  

a FHIR Parameters resource, one row per row

  

handing the rows to another FHIR system

The same two patients as NDJSON:

$ raco sql-on-fhir run patients.view.json data/

{"birth_date":"1974-12-25","family":"Lee","gender":"female","id":"ann"}

{"birth_date":"1990-03-01","family":"Ortiz","gender":"male","id":"bob"}

Three details matter when another program reads the output:

  • Column order. CSV and fhir keep the view’s column order. In the two JSON formats each row’s keys are in alphabetical order; read them by name.

  • Empty cells. An empty cell is nothing between the commas in CSV, null in JSON, and left out of the row in fhir.

  • Types. JSON keeps numbers as numbers, true and false as themselves, and a collection column as a list. CSV is text: a list is written as its JSON ("[""Ann"",""Marie""]"), a cell containing a comma or a quote is quoted, and lines end with a carriage return and a line feed, as the CSV standard (RFC 4180) says.

Parquet, a format the specification also names, is not written.

4.3 A view written as Racket forms🔗

The same view can be written in a file that starts with #lang sql-on-fhir, as nested forms in place of JSON. What you gain is earlier checking: the file is a Racket module, and a misspelt element or a status outside its list stops it from compiling. This is readings.sof:

#lang sql-on-fhir

(ViewDefinition

 (name "bp_readings") (status "active") (resource "Observation")

 (where (ViewDefinitionWhere (path "code.coding.exists(system = 'http://loinc.org' and code = '85354-9')")))

 (select (ViewDefinitionSelect

          (column (ViewDefinitionSelectColumn (name "patient") (path "subject.getReferenceKey(Patient)"))

                  (ViewDefinitionSelectColumn (name "date") (path "effective.ofType(dateTime)"))

                  (ViewDefinitionSelectColumn (name "systolic")

                    (path "component.where(code.coding.code = '8480-6').value.ofType(Quantity).value"))))))

It runs the same way, whatever the file is called:

$ raco sql-on-fhir run readings.sof data/ --format csv

patient,date,systolic

ann,2024-03-01T09:00:00Z,152

ann,2024-04-02T09:30:00Z,138

racket readings.sof prints the view as JSON, the form to give to another tool.

The forms are the specification’s elements, in the form syntax of the family’s fhir/r6 language: ViewDefinition; ViewDefinitionWhere; ViewDefinitionSelect (with column, a nested select, forEach, forEachOrNull, repeat, unionAll); ViewDefinitionSelectColumn (path, name, description, collection, type, tag); and ViewDefinitionConstant. A mistake names the form:

ViewDefinition: unknown field ViewDefinition.resorce

  at: resorce

  in: (resorce "Observation")

 

ViewDefinition: "live" is not in the required value set for ViewDefinition.status (http://hl7.org/fhir/ValueSet/publication-status); valid codes: (active draft retired unknown)

The repository’s examples/patient-demographics.rkt is a view written this way.

4.4 From a Racket program🔗

view-rows takes a view as JSON and gives its rows, each a hash from column name to value. Give it the records, or let it read them from the current data source, the family’s way of naming where data is (a folder, records in memory, a server’s store):

(require json fhir/data-source (only-in sql-on-fhir/operations view-rows))
(define (read-file f) (call-with-input-file f read-json))
(define view (read-file "patients.view.json"))
 
(view-rows view (map read-file '("data/ann.json" "data/bob.json")))
; => (list (hasheq 'id "ann" 'family "Lee" 'gender "female" 'birth_date "1974-12-25")
;  (hasheq 'id "bob" 'family "Ortiz" 'gender "male" 'birth_date "1990-03-01"))
 
(parameterize ([current-data-source (directory->data-source "data/")])
  (view-rows view))                  ; the same rows, from the folder

A module written in #lang sql-on-fhir provides its views: resources (the typed ViewDefinitions), (->nodes) (the same) and (->json) (as JSON, what view-rows takes).

(require (only-in "readings.sof" [->json views])
         fhir/data-source (only-in sql-on-fhir/operations view-rows))
(parameterize ([current-data-source (resources->data-source observations)])
  (view-rows (car (views))))
; => (list (hasheq 'patient "ann" 'date "2024-03-01T09:00:00Z" 'systolic 152) …)

4.5 As a FHIR operation🔗

The specification defines two operations, named requests a FHIR system can answer: $sql-run runs one view and answers its rows, and $sql-export runs several. Both are here as procedures, built on the specification’s own definitions, so a server can offer them and a program can call them.

(require fhir/operation fhir/data-source sql-on-fhir/operations)
(parameterize ([current-data-source (directory->data-source "data/")])
  ($sql-run view #:_format "csv")                       ; the view is the subject
  (apply-operation "$sql-run" #:subjectCanonical "http://example.org/ViewDefinition/x" #:_format "fhir")
  ($sql-export #:subject (list view) #:_format "csv"))

$sql-run answers CSV, NDJSON or JSON as a FHIR Binary resource (the text, base64-encoded) and fhir as a Parameters of rows. The view is given directly, or named by its url (#:subjectCanonical) or its reference (#:subjectReference) and found in the data source. The data is the data source’s, or records given with #:resource. #:patient keeps one patient’s records, #:_since those updated after a time, #:_limit the first rows, and #:header "false" leaves the heading out of CSV.

A view that is refused, or that fails on the data, raises exn:fail:operation carrying an OperationOutcome, FHIR’s resource for reporting a problem; a path with several values for one cell has the code processing.

$sql-export answers at once with a Parameters resource: an exportId, the status completed, and one output per view with its result inside as a Binary.

To offer both over HTTP, fhir-server serves any operation value:

(require fhir/data-source sql-on-fhir/operations (only-in fhir/capability/operations serve-operations))
(parameterize ([current-data-source (directory->data-source "data/")])
  (serve-operations (list $sql-run $sql-export) #:port 8080))

A POST of a Parameters resource to /$sql-run, holding the view as subjectResource and _format csv, is then answered with the CSV.

5 For an AI agent, and in an editor🔗

  • For an agent. In an fhir-mcp workspace a *.view.json file is a ViewDefinition, checked as it is written: a path naming an element the record type lacks is reported at its place in the file, with the nearest name. run gives the view’s rows over the workspace’s data. explain of one record shows the rows that record alone produces, the rows it would produce without the where, and whether each where holds for it. Every view is also a table that the workspace’s SQL queries can read, which is where the SQL in the name comes in. The repository’s guide.md is the format written for an agent to read (fhir-mcp serves it as learn://sql-on-fhir), and .claude/skills/sql-on-fhir is the same workflow for an agent using the command line.

  • In an editor. The family’s language server does not cover views. A JSON view is checked when it runs; a #lang sql-on-fhir file is checked when it compiles.

6 Limits🔗

  • No database. The command makes the table; it does not run SQL. Views are evaluated in memory, one list of rows per view. To query the result, load the CSV or NDJSON into the database or spreadsheet you use, or work in a fhir-mcp workspace, where views are tables.

  • The command line reads data as FHIR R6. Most elements have the same name in R4, R5 and R6, and such data reads as it is. An element that R6 renamed or removed is not read, and its column is empty with no message: R4’s medicationCodeableConcept on a MedicationRequest is one. (A fhir-mcp workspace reads data in the workspace’s own FHIR version.)

  • $sql-run ignores the inputs parameters, context, group and source; a patient that does not resolve filters to nothing; its subject is a ViewDefinition only (not the specification’s SQLQuery or SQLView Libraries); it does not write Parquet.

  • $sql-export finishes at once, with the results inside its answer as Binaries. There is no background job, polling, cancellation or download address, and _format=fhir becomes NDJSON.

  • Columns. A column’s type and tag are not enforced. Constants must be simple values (text, numbers, true or false, dates, codes).

  • Missing elements. The check catches a misspelt element and a value outside its allowed list. It does not notice a required element that is absent: a view without status runs, and a view without resource fails with a message about the program’s internals.

  • References. getReferenceKey() reads relative references (Patient/ann); an absolute address gives an empty cell.

  • Module errors at the command line. When a #lang sql-on-fhir file does not compile, run prints Racket’s own error with its context lines, not the one-line form a JSON view gets.

7 Words used here🔗

  • FHIR: the health-care standard for records exchanged between systems. Resource: one record of a given kind (a Patient, an Observation), written as JSON.

  • Bundle: one FHIR file that holds many resources.

  • ViewDefinition, or view: the JSON file that describes a table over one kind of resource: its filters and its columns.

  • Column: a name and a path; row: one line of the table, for one resource or one item inside it.

  • FHIRPath: the language of every path, for pointing at values inside a resource (name.family.first()).

  • forEach, forEachOrNull: make a row per item of a repeating element; the second keeps a resource that has none. where: a filter on resources. unionAll: stack alternatives. repeat: follow a path to any depth.

  • Collection: a column whose cell may hold a list.

  • Constant: a named value a view’s paths use as %name.

  • Key: a value two tables share so they can be joined: a resource’s id (getResourceKey()) and the id a reference names (getReferenceKey()).

  • Choice element: an element that can hold one of several types, written with the type in its name (valueQuantity); in a path, value.ofType(Quantity).

  • Value set: a fixed list of allowed codes, such as the four a status may be.

  • CSV: comma-separated text, one row per line. NDJSON: one JSON object per line.

  • The specification, or IG (implementation guide): the published SQL on FHIR standard. Its package is the machine-readable copy this tool’s model is generated from.

  • Operation: a named request a FHIR system answers, written with a dollar sign ($sql-run). Parameters, Binary, OperationOutcome: the FHIR resources for an operation’s inputs and outputs, for raw content, and for a reported problem.

  • Canonical: the url that names a definition such as a view, wherever it is stored.

  • Data source: the family’s value for "where the data is": a folder, resources in memory, or a server’s store.

8 How it is tested🔗

  • The test suite the SQL on FHIR project publishes for implementations to share: 144 of 144 tests give the expected rows, and every view the suite calls invalid is refused. raco sql-on-fhir tck runs it.

  • The ViewDefinition model is generated from the specification’s published package (version 3.0.0-ballot), not written by hand, so what a view may contain is what the standard says. raco sql-on-fhir check verifies the generated files are current.

  • Every view in the repository’s guide.md is checked by the tests, and its examples give the rows the text states. This manual is rendered by a test that fails on a broken reference.

raco test . in the repository runs all of it. The repository’s TESTING.md says where the suite and the package come from and how to run each check. Both are copied into the repository unchanged: the specification’s package under the CC0-1.0 licence, the test suite under MIT, as this package is.
